# 项目即协作空间：产品目标与边界说明

- 日期：2026-09-18
- 状态：目标理解与架构分析，不代表业务改造已经完成
- 适用范围：OpenAgents 当前项目界面及原工作区协作模型

## 1. 文档目的与阅读约定

本文把已经确认的用户目标展开为一份可用于产品讨论、架构设计和后续验收的共同依据。核心不是如何把界面中的“工作区”三个字替换为“项目”，而是明确：原来由工作区承担的协作职责，应当如何整体转交给项目。

本文区分四类内容：

- **已确认目标**：用户明确表达并确认的产品要求，后续实现不能偏离。
- **必要推论**：为了使已确认目标成立，系统必须具备的行为或边界。
- **实现建议**：结合现有代码提出的可选技术路径，不等于已经批准的实现方案。
- **待确认事项**：当前目标没有决定的产品细节，不能在开发时默认为用户要求。

用户提供的截图用于理解界面结构，不是对后台数据归属、权限规则或功能完成度的证明。当前代码分析是本地工作树的阅读快照，包括正在开发的项目动态相关代码；本文没有通过运行服务验证其完整行为。

## 2. 一句话定义目标

**项目本身就是团队进入、协作和管理权限的空间。用户通过项目列表选择或新建项目，进入后使用同一套项目页面；当前项目决定页面中的成员、内容和操作权限。产品中不再存在需要用户单独理解或切换的工作区。**

这里的“项目”不是以下任一种东西：

- 工作区内部的分类、文件夹或标签。
- 仅用于切换标题和面包屑的前端卡片。
- 为某个客户或团队单独开发的一套页面。
- 所有用户共用的一份全局数据的不同视图。
- 只管理任务、不承担成员和权限管理的轻量容器。

项目应当具备原工作区作为协作空间的实质能力，而不只是继承它的名称。

## 3. 对用户表达的深度解析

### 3.1 “不想要工作区的概念”

这是对产品概念层级的要求，不只是文案要求。

用户不应先回答“我要进入哪个工作区”，再回答“我要进入哪个项目”。项目就是确定协作范围的那一次选择。团队关系、资料归属和管理入口应当能在项目中被理解，不需要再借助另一个上层空间解释。

底层为了兼容协议暂时存在 `workspace_id`，与产品继续存在独立工作区，是两件不同的事。前者可以是技术实现细节；后者会重新引入用户已经明确要消除的概念。

### 3.2 “所有人进来都是这个界面”

这句话已经被用户进一步限定为：同一项目的成员共享该项目的页面和数据，各项目复用同一套页面结构。

它不意味着所有人拥有同样的权限，不意味着所有人自动加入同一个团队，也不意味着项目 A 与项目 B 共用数据。不同用户可以看到不同的项目列表，同一个用户在不同项目中也可以具有不同角色。

固定的是产品布局和功能结构；变化的是当前项目的上下文。

### 3.3 “通过项目体现工作区的概念”

其本质是协作职责的承接：把工作区原有的团队入口、成员关系、共享资源和权限边界交给项目。

项目不需要在界面里解释“我实际上是一个工作区”。用户只需要知道：进入这个项目，就是进入这个团队围绕该项目共同工作的空间。

### 3.4 “项目不是工作区下面的一层分类”

这是对实体关系最明确的约束。目标不是继续维持“工作区拥有多个项目，工作区成员默认访问全部项目”的结构。

项目 A 的成员关系应当独立成立。一个人加入 A，不能由于属于某个隐含共同工作区而自动获得 B 的访问权。在现有代码中的本地项目分类外面继续包着同一个授权容器，即使界面隐藏了容器名称，也没有满足这个目标。

### 3.5 “动态、计划和成员管理可以逐步实现”

这决定的是交付顺序，不是最终职责。

这些入口可以暂时没有完整内容；但任务、文件、工作流、浏览器和知识库既然被放进当前项目，就必须真正属于当前项目。成员管理界面可以后做，后台用于判断谁有权访问哪个项目的成员关系不能因此省略。

## 4. 必须始终成立的产品约束

| 编号 | 约束 | 含义 |
| --- | --- | --- |
| G-01 | 项目是协作边界 | 团队进入、共享内容、角色管理围绕项目成立 |
| G-02 | 无独立工作区操作 | 用户不需要创建、选择或切换项目之外的工作区 |
| G-03 | 用户可以参与多个项目 | 一个账号通过独立成员关系关联多个项目 |
| G-04 | 页面结构复用 | 不因项目数量增加而复制页面代码或开发专用页面 |
| G-05 | 数据随当前项目切换 | 项目页各模块不能继续读取同一份上层空间数据 |
| G-06 | 成员和角色属于项目 | 同一人在 A 中的成员资格与角色不能自动应用到 B |
| G-07 | 项目成员共同协作 | 共享项目资源，不是每个成员各有一份个人副本 |
| G-08 | 共享不等于无限权限 | 能否邀请、编辑、执行或删除由项目内角色决定 |
| G-09 | 人类与智能体分开管理 | 加人进团队与连接智能体不是同一种成员操作 |
| G-10 | 允许分阶段完成内容 | 占位入口可以保留，但项目隔离不能只存在于界面 |

## 5. 当前代码结构与目标的距离

### 5.1 与此次目标相关的代码位置

主要业务界面位于 `workspace/frontend`，使用 Next.js 和 React。业务后台位于 `workspace/backend`，使用 FastAPI 和 SQLAlchemy。`sdk`、`packages/agent-connector` 和 `packages/launcher` 提供智能体协议、连接和本机运行等能力。

目标涉及的重点不是重写整个仓库，而是重整前后端业务中的协作实体、上下文与授权方式，并保持智能体执行路径的范围一致。

### 5.2 当前是两套含义不对等的“空间”

当前后端的 `Workspace` 是一个实际的 ONM 网络和协作容器。会话、任务、文件、知识条目、工作流、浏览器资源、智能体成员和设备等都通过它归属和授权。

前端项目列表则主要是存储在浏览器中的项目记录。项目页已经复用公共布局，但多数业务模块仍然借用当前工作区的上下文。因此，前端“项目”与后端“协作空间”还不是同一个实体。

当前大致关系为：

```text
账号
  -> 工作区成员关系
  -> 当前工作区：实际的数据、权限与执行范围
       -> 本地项目列表
       -> 项目页面
            -> 多数模块继续使用当前工作区数据
```

### 5.3 已有能力与主要缺口

| 方面 | 当前代码状态 | 与目标的距离 |
| --- | --- | --- |
| 项目列表 | 项目创建、重命名、删除主要修改 `localStorage`；保存键还包含当前工作区 ID | 不是服务器维护的协作空间列表，也不能保证成员跨设备看到一致结果 |
| 项目页面 | `ProjectInternalPage` 已复用八个标签页的公共结构 | 布局方向正确，但布局复用不能证明数据与权限已独立 |
| 业务模块 | `ProjectWorkspaceContent` 直接嵌入原任务、文件、工作流、浏览器和知识库组件，没有建立独立项目范围 | 切换本地项目不等于切换这些模块的后台数据归属 |
| 动态会话 | 当前开发代码通过 `project:<项目ID>:` 前缀分类会话，并在前端筛选 | 有项目分类，但字符串前缀本身不是后端成员和权限边界 |
| 计划 | 计划记录主要保存在本地，处理人选项读取工作区人类成员和智能体 | 计划记录和可选成员尚未统一为真实项目范围 |
| 人类成员管理 | 原设置页通过工作区团队接口邀请、查看成员和修改角色；项目中的成员标签尚未接入完整内容 | 管理对象仍是工作区，不能直接等同于本地项目成员 |
| 前端上下文 | `WorkspaceProvider` 集中持有业务状态；可变的 `WorkspaceApi` 实例配置一个当前工作区 | 需要保证未来项目切换时，状态、请求与订阅共同切换，而不只是更换选中项目 |
| 登录入口 | 首页仍根据部署模式显示账号工作区首页、本地工作区或介绍页 | 需要收敛到项目选择与统一项目页面的产品流程 |
| 后台授权 | 现有成员角色以工作区为范围；机器 token 路径具有高度信任 | 可复用部分能力，但不能让兼容 token 绕过新的项目内人类角色规则 |

这些是结构阅读结论，不是针对现有功能的完整安全审计。尤其不应把当前开发中的“动态已经有项目会话”误判为“项目已经是协作容器”。

## 6. 目标中的概念与关系

### 6.1 账号

账号表示“这个人是谁”，是跨项目的身份。一个人在不同项目里还是同一个人，但不是在所有项目里都拥有同一种身份或权限。

### 6.2 项目

项目表示“我们正在共同进入哪个协作空间”。它拥有项目级成员关系、共享业务资源，以及支撑这些资源执行的授权范围。

### 6.3 项目成员关系

项目成员关系表示“这个人是否属于这个项目，以及在这里具有什么角色”。其核心是用户与项目之间的关联，不是用户账户上的单一全局角色。

例如：同一用户可以是 A 的管理员、B 的普通成员，并且不是 C 的成员。修改 A 中的角色不能同时修改 B 中的角色。

### 6.4 当前项目上下文

当前项目上下文是界面正在使用的项目身份、成员信息、资源范围和能力集合。它连接同一套页面模板与不同项目的实际内容。

选中项目是界面状态；访问项目是后台授权结果。不能因为用户修改了 URL 或浏览器状态，后台就承认其项目访问权。

### 6.5 目标关系

```text
用户账号
  -> 项目 A 成员关系：角色 A
       -> 公共项目页面模板 + 项目 A 上下文
            -> A 的成员、任务、文件、工作流、浏览器、知识库
  -> 项目 B 成员关系：角色 B
       -> 同一个公共项目页面模板 + 项目 B 上下文
            -> B 的成员、任务、文件、工作流、浏览器、知识库
```

这里没有独立的“先加入工作区，再进入项目”的用户操作层。页面可以复用，成员和内容不能因此合并。

### 6.6 原工作区职责的交接清单

“整体交接”应按职责核对，而不是按旧界面的位置机械搬运：

| 原协作职责 | 项目应当如何承接 |
| --- | --- |
| 团队进入与选择 | 项目列表选择或新建真实项目，进入后建立该项目上下文 |
| 人类成员与邀请 | 邀请关联当前项目，接受后只建立指定项目的成员关系 |
| 人类角色与管理权 | 操作能力按本项目角色判定，不借用另一项目的角色 |
| 共享内容与资源 | 原协作内容由项目拥有，列表、详情、引用和操作范围保持一致 |
| 协作交流与执行 | 会话、任务和工作流的执行与结果写回保留原项目身份 |
| 智能体接入与管理 | 与人类成员管理分开，但执行授权仍对应具体项目 |
| 协作环境配置 | 会影响项目共享资源或执行权限的配置，应有明确项目范围和管理授权 |
| 生命周期与访问撤销 | 项目归档、成员移除或授权撤销，应对该项目的访问和执行路径产生一致影响 |

最后两项是完整承接协作容器职责所需考虑的范围，不代表用户已经确定了归档、删除、环境配置等功能的详细设计。

同时，账号身份和个人界面偏好并非项目团队权限，不应随项目切换而被当作另一份账号。模型访问、第三方集成、技能资产及计费等现有配置，还需要逐项确认所有权与授权范围，不能因为曾存在于工作区设置中就全部机械改为项目资产。

## 7. 入口、页面结构与项目切换

### 7.1 项目列表的职责

项目列表是协作空间的选择和创建入口，而不是某个工作区内部的本地分类列表。

必要行为包括：

- 展示当前用户按权限可以进入的项目。
- 允许用户按产品策略新建项目；新建权限和数量限制尚待确认。
- 进入项目时解析真实项目身份并校验访问权。
- 在不同浏览器或设备上，根据相同账号和成员关系获得一致的可访问项目集合。
- 无项目时能够显示正常的空状态，不要求先创建一个工作区才能继续。
- 将“项目不存在”“没有权限”和“加载失败”与正常空项目区分处理。

创建项目必须产生服务器端真实协作实体，并建立符合策略的创建者访问关系。不能把只在本机出现的新卡片当作项目创建成功；创建失败也不应留下被误认为可供团队进入的项目。

是否默认进入上次访问的项目、是否只有一个项目时自动进入，以及登录后的默认标签页，仍是待确认的交互细节。

### 7.2 项目页面的固定结构

所有项目复用同一套项目页面，顶部包含：动态、计划、任务、文件、工作流、浏览器、知识库、成员管理。

进入 A 和进入 B 不需要两套路由实现、两套组件目录或按项目名称写条件分支。项目名称、资源数量和成员不同，是上下文差异，不是页面类型差异。

角色可以影响操作按钮是否可用，但不需要因此为管理员和普通成员各开发一套项目页面。

### 7.3 应用级界面与项目级业务的区别

品牌、账号身份、个人界面偏好和项目选择入口可以存在于应用级界面中；项目页的业务内容由当前项目决定。左上角的产品品牌不应继续承担选择独立工作区的职责。

截图左侧的新对话、定时任务、知识库、收件箱、技能中心、智能体及全部会话，目前还没有全部被用户明确指定为“当前项目入口”“个人入口”或“跨项目汇总入口”。本文不擅自决定它们的最终归属，也不以此额外引入一个个人工作区。

但有一条确定的约束：这些入口不能让项目页的八个模块重新退化为一份上层全局数据。若未来提供跨项目汇总，每条记录必须保留原项目归属，并按用户对原项目的权限授权。

### 7.4 项目切换应当是上下文切换

从 A 切换到 B，应当形成一个完整过程：

1. 确定 B 的项目身份，并校验当前用户是否可以进入。
2. 让 A 的界面订阅和轮询退出当前页面，隔离尚未完成的请求结果。
3. 重置或按项目恢复文件选中项、任务详情、浏览器标签、筛选条件等页面状态。
4. 建立 B 的资源范围、成员范围和操作能力。
5. 加载 B 的内容；加载期间不能把 A 的内容冒充为 B 的内容。
6. 后续操作以其发起时明确的项目范围执行。

特别需要避免两个问题：A 的慢请求在切换后覆盖 B 的页面；A 中已发起的异步写入因全局 API 配置变化而被错误地发送到 B。

切换页面也不等于取消 A 的后台任务。后台执行的生命周期应由任务自身和项目权限决定，不能由用户是否正在浏览 A 决定。

## 8. 八个项目功能的职责

| 功能 | 项目内职责 | 必须保持的边界 | 当前目标允许的交付状态 |
| --- | --- | --- | --- |
| 动态 | 承载当前项目的协作交流或动态内容 | 若有会话和消息，只能归属当前项目；具体动态产品形态待确认 | 可以先保留入口，再逐步实现 |
| 计划 | 承载当前项目的协作规划 | 计划及处理人范围不能借用另一项目的数据；未来记录应支持共享 | 可以先保留入口，再逐步实现 |
| 任务 | 当前项目成员共同查看和操作任务，按权限执行或管理 | 任务、附件、运行会话及执行结果归属同一项目 | 应实现真实项目归属 |
| 文件 | 当前项目共享文件的管理与访问 | 列表、下载、预览、上传、回收站和恢复操作均受项目权限约束 | 应实现真实项目归属 |
| 工作流 | 当前项目的流程模板和执行能力 | 模板、步骤使用的执行者、运行状态和结果均保持项目范围 | 应实现真实项目归属 |
| 浏览器 | 当前项目可共同查看和操作的浏览器资源 | 标签、远程会话、持久上下文和登录状态不能无意跨项目共享 | 应实现真实项目归属 |
| 知识库 | 当前项目共享的知识资料 | 列表、正文、附件及任务引用均验证项目归属 | 应实现真实项目归属 |
| 成员管理 | 邀请人加入当前项目、查看成员、管理项目内角色 | 邀请、接受、角色修改、移除均只能影响指定项目 | 可以先保留入口，管理内容逐步实现 |

“共同查看和操作”指这些是项目共享资源，成员能在自己的角色允许范围内协作；不是要求每个角色都可以执行所有编辑、删除和管理操作。

### 8.1 资源之间的关联也要遵循项目边界

不能只给任务列表加项目筛选，而允许 A 的任务引用 B 的文件；也不能只给工作流模板分项目，却让模板在执行时读取 B 的知识库或控制 B 的浏览器。

项目归属需要贯穿创建、引用、读取、执行和结果写回。跨资源操作应同时检查各资源的项目身份。

未来若确实需要跨项目引用，应设计明确的授权或复制机制，不能把它当作默认能力。当前目标没有要求跨项目共享资源。

### 8.2 浏览器资源的共享需要进一步限定

属于同一个项目，不等于多个成员可以无冲突地同时控制同一个远程浏览器。标签可见性、控制权、并发编辑、登录凭据和持久会话复用都需要专门设计。

本目标已经确定浏览器资源是项目级资源；但尚未确定实时共控、控制锁或凭据共享策略。隔离不能止于数据库记录，还应覆盖远程会话和持久化存储使用的实际范围。

## 9. 人类成员与角色管理

### 9.1 成员管理管理的是“本项目的团队”

最终的成员管理入口应当能够回答：这个项目有哪些人、谁正在被邀请加入、每个人在本项目里是什么角色、当前用户可以管理哪些关系。

“邀请成员”必须携带当前项目身份。邀请某人加入 A 后，应当只建立或更新其与 A 的关系，不能顺带将其加入 B。

在 A 中移除某人，应撤销其对 A 的后续访问和操作能力，但不能删除其账号或撤销其在 B 的成员关系。

### 9.2 身份、成员资格和能力是三次不同判断

```text
确认调用者身份
  -> 判断是否有权访问目标项目
  -> 判断其项目内角色是否允许这次操作
  -> 判断目标资源确实属于该项目
```

登录成功只证明“这个人是谁”，不能证明“这个人是这个项目的成员”。进入了项目也不能证明其有权邀请成员、修改角色或删除资源。

### 9.3 角色体系的实现建议

现有后台已经有 `owner`、`admin`、`member`、`viewer` 四类角色，可以作为改造时的候选基础。以下只是建议，并不是用户已确定的完整角色权限表：

- 负责人：处理项目所有权及重要项目管理操作。
- 管理员：在明确授权范围内管理成员和项目资源。
- 普通成员：参与项目业务协作，不默认拥有成员或角色管理权。
- 只读成员：查看允许访问的项目内容，不执行写入或智能体操作。

具体哪些角色可以邀请、执行工作流、控制浏览器、删除文件，以及负责人转移和最后一名负责人的保护规则，需要后续确定。确定后必须由后台执行，前端按钮隐藏只是交互呈现。

### 9.4 邀请链接不等于页面分享链接

分享项目页面地址，只提供一个定位入口，不自动赋予成员资格。有效的人类邀请应关联具体项目和拟授予角色，并具有可验证的接受流程。

邀请过期、撤销、重复接受、受邀者身份不匹配等状态需要明确处理。可以复用现有工作区邀请能力，但其最终作用范围必须与项目一致。

是否允许无需登录的公开项目或公开只读快照，当前未被确认。默认不能用“拿到链接就能访问”的行为替代项目成员授权。

## 10. 智能体与人类成员的区别

人类成员决定团队协作与管理权限；智能体是参与项目执行的程序或运行实例。两者可以出现在同一个项目中，但不应混用身份、邀请入口或角色含义。

| 维度 | 人类成员 | 智能体 |
| --- | --- | --- |
| 身份来源 | 用户账号身份 | 程序身份、连接凭据或运行节点 |
| 加入含义 | 获得指定项目的成员资格及角色 | 获得参与指定项目执行的授权或绑定 |
| 管理目标 | 邀请、成员列表、角色修改、移除 | 连接、运行状态、能力配置、执行范围、断开 |
| 是否等价 | 不能因为能连接智能体就自动取得人类管理员身份 | 不能因为某人加入项目就推断其智能体已经接入 |
| 跨项目关系 | A 的成员资格不自动成为 B 的成员资格 | A 的执行授权也不能自然扩展为 B 的执行授权 |

用户明确要求区分这两类管理，但没有决定智能体是账号资产、项目资产，还是可被多个项目授权复用的资产。

“连接一次智能体，在多个项目使用”是一个可以后续考虑的能力，不能作为本次目标已经确认的要求。即使采用复用模型，也应独立表达项目授权，并隔离运行会话、工具访问、上下文和结果写回范围。

此外，项目级数据库隔离不自动保证机器上的工作目录、运行进程或凭据隔离。若多个项目使用同一节点，需要明确其真实执行环境的信任与隔离策略。

## 11. 数据与权限如何体现项目本体

### 11.1 概念模型

在产品和业务语义上，至少需要这些关系：

```text
User
Project
ProjectMembership(user_id, project_id, role)
ProjectInvite(project_id, intended_role, ...)
ProjectResource(project_id, ...)
ProjectAgentAuthorization(project_id, agent_identity, ...)
```

这是概念模型，不是要求立即新增以上所有数据库表。现有工作区表和成员表若与项目建立准确的一一对应关系，可以暂时承载这些语义。

共享内容应由服务器维护。`localStorage` 可以保存项目内的视图偏好、尚未提交的草稿或缓存，但不能成为多人共享项目、成员关系和业务内容的唯一事实来源。

### 11.2 必要的数据约束

- 项目有稳定身份；项目名称改变不应改变资源归属。
- 项目成员关系以项目和用户为范围，不能通过一个全局角色推导所有项目权限。
- 项目资源有明确归属，或能通过经过校验的关联确定唯一项目归属。
- 读取单条资源时也检查访问权，不能只在列表接口筛选。
- 附件、知识引用、工作流步骤与运行会话等关联保持项目范围一致。
- 创建与执行时确定项目范围，不能把前端最后选中的项目作为延迟写入的默认归属。
- 缓存和订阅以项目区分；包含用户私有偏好或权限相关结果时，还应以用户身份区分。

### 11.3 权限需要覆盖所有访问路径

项目权限不仅约束页面请求，还约束搜索、文件预览和下载、事件流、会话发现、后台执行、通知内容及智能体工具访问。

只在前端过滤数据，不构成安全边界。只给 REST 接口加项目权限，也不代表事件流或工具接口已经满足同样的规则。

成员被移除后，应停止其后续读取和写入，并使相关订阅和权限缓存失效。已经被合法下载到本地的文件不能凭空收回；带有效期的下载地址、长期 token 和已有订阅需要单独处理撤销或到期策略。

### 11.4 现有机器 token 的兼容问题

当前后台的工作区共享 token 和节点 token 属于高度信任的机器凭据，可以绕过人类角色等级判断；账号工作区列表还会向非只读成员返回共享 token。

若直接把这些能力迁移为项目接口，却仍让普通人类成员使用高度信任 token，就可能使项目内角色限制失去实际作用。改造必须审视凭据发放和使用方式，而不能只修改角色文案。

建议人类请求以账号身份和项目成员角色授权，机器请求采用明确范围的执行凭据。具体的机器能力收敛和兼容期限应在实施方案中确定，本文不假设现有所有客户端已经支持这一变化。

## 12. 与现有架构衔接的建议

### 12.1 第一阶段可复用现有 Workspace 作为项目的后台容器

现有 `Workspace` 已经承担成员、共享资源和智能体网络范围，第一阶段可以让它完整对应一个用户可见项目。

对应关系应是：

```text
一个用户可见项目
  <-> 一个旧 Workspace 后台协作容器
  <-> 一个与其一致的执行网络范围
```

这不是“项目放在工作区里”。用户可见项目与旧容器表示的是同一个协作实体，旧表名只是暂时保留的实现名称。

项目列表应读取这些真实协作实体及其成员关系，而不是继续在一个旧 Workspace 内维护若干互不独立的本地项目。

### 12.2 为什么不建议先全面重命名

本次目标的成败取决于行为是否成立，而不是源码是否完全没有 `workspace` 这个单词。大量数据库、接口、事件和连接器重命名会扩大改造范围，却不必然修复数据隔离。

合理顺序是先建立准确的项目语义、范围和用户流程，再逐步处理 API 名称、表名、SDK 命令及兼容文档。

可以暂时保留 `workspace_id`；不能暂时保留“多个项目共用一套工作区成员权限”的实际协作模型，并声称目标已完成。

### 12.3 若改为独立 Project 模型

另一个可选路径是新增或迁移为独立项目模型，并改造所有资源归属及权限路径。这个路径同样能满足目标，但数据迁移、协议兼容和测试范围更大。

若运行时还需要内部网络实体，应说明它是项目执行实现，而不是在项目之外再引入一个供用户管理的上层团队空间。仅新增 `projects` 表，但其权限仍继承一个多人共享工作区，并不能解决用户指出的问题。

本文不把某一种表结构作为已确认目标；判断标准始终是项目是否真正承担完整协作职责。

## 13. 存量数据与渐进交付

### 13.1 存量旧工作区可以映射为项目

由于当前真实数据归属在旧 Workspace 上，一个保守的迁移起点是将每个旧工作区映射为一个真实项目，并保留其资源和成员范围。

这仍是建议，具体执行前需要核对存量数据、成员来源和凭据情况，不应自动进行破坏性迁移。

### 13.2 本地项目不能直接当作已存在的团队项目

浏览器里的项目记录可能只是分类或演示数据。同一个旧工作区下的不同本地项目，可能展示过同一批任务和文件。现有资源缺少独立本地项目归属，不能依据项目卡片名称推断应怎样拆分。

应单独决定本地项目和计划的处理方式，例如受控导入、人工确认归属或保留为待迁移数据。不能自动把同一份共享资源复制给所有新项目，更不能把本地卡片删除视为真实项目及数据删除。

### 13.3 允许分阶段，但每阶段要准确描述完成度

建议分为以下阶段，不作为已经批准的排期：

1. 确立项目实体与成员范围，收敛项目列表及进入项目的流程。
2. 将任务、文件、工作流、浏览器、知识库的读取、写入与执行绑定真实项目。
3. 验证切换、深链接、事件订阅、后台任务和跨资源引用不串项目。
4. 逐步完善动态、共享计划与项目内成员管理界面。
5. 整理存量迁移及旧接口、命令和内部名称的兼容策略。

阶段 4 的成员管理界面可以后做，但前面阶段仍需要有效的后台成员关系和受控的授权管理方式，否则无法验证谁能进入哪个项目。

“项目页面结构完成”“项目数据隔离完成”和“成员管理功能完成”应分别报告，不能互相替代。

### 13.4 本地单用户模式不等于多人项目模型

现有 `LOCAL_MODE` 是免账号认证的本地单用户部署方式。它可以帮助本机开发或演示，但不能直接作为多人项目权限系统。

让所有访问者都拿到同一份高度信任凭据，只会让大家进入同一容器；这不满足多个项目独立成员和角色的要求。

## 14. 场景推演与验收标准

以下场景既验证产品理解，也可作为后续测试依据。涉及暂未实现的入口，应在对应功能阶段补齐测试。

### 场景 A：同一项目的多人协作

甲和乙都是项目 A 的成员。甲在 A 创建任务、上传文件，乙用自己的账号和另一台设备进入 A。

验收：乙在权限允许范围内能看到服务器维护的同一份 A 内容，而不是自己的本地项目副本。乙的修改应在正常同步机制下对甲可见；不要求本文尚未确定的即时同步时延。

### 场景 B：加入 A 不代表加入 B

甲只属于 A，乙属于 A 和 B。

验收：甲不能因进入 A、拿到 A 的邀请或知道 B 的 URL/资源 ID 而读取 B 的成员、文件、任务和知识。乙进入 B 时使用的是 B 的成员关系。

### 场景 C：同一人具有不同项目角色

乙在 A 是管理员，在 B 是普通成员。

验收：乙在 A 可以进行被授权的管理操作，切到 B 后不应保留 A 的管理能力。直接调用接口也不能绕过 B 的角色判断。

### 场景 D：项目切换与慢请求

乙打开 A 的文件详情，在请求完成前切换到 B。

验收：A 的延迟结果不能覆盖 B 的列表或预览；A 的文件选中状态不能触发一次对 B 归属的错误操作。返回 A 后可以按明确策略恢复其自己的视图状态。

### 场景 E：人类邀请与智能体连接

管理员在 A 的成员管理入口邀请丙，又为 A 接入一个智能体。

验收：丙接受后获得的是 A 的人类成员角色；智能体以独立程序身份参与 A。两者不混入同一套角色推断，也不能由其中一个操作自动授予 B 的权限。

### 场景 F：移除成员

丙同时属于 A 和 B，随后被移出 A。

验收：丙的后续 A 请求、写入和订阅按撤销策略被拒绝或终止，但其 B 成员资格不变。不会因为移除 A 成员而删除丙的账号。

### 场景 G：跨资源引用

尝试给 A 的任务关联 B 的文件、知识条目或工作流。

验收：后台拒绝不符合项目归属规则的关联，不能只依赖前端下拉列表没有提供这些选项。

### 场景 H：切换期间的后台执行

乙启动 A 的任务，然后进入 B。A 的智能体稍后生成文件并写回结果。

验收：任务继续按其生命周期运行，结果仍写回 A；不会因为乙当前正在 B 而改变结果归属或执行工具的权限范围。

### 场景 I：刷新、深链接与跨设备

成员直接打开 A 的文件或项目标签页链接，刷新页面，或在另一设备访问。

验收：项目上下文可以由真实身份和授权重新建立，不需要提前点击本地项目卡片。链接参数中的项目名称不作为后台事实来源；篡改参数不会获得访问权。

### 场景 J：入口可以占位，数据不能假隔离

项目页保留动态、计划和成员管理标签，但其中部分内容暂未完成。

验收：任务、文件、工作流、浏览器和知识库仍属于当前真实项目。不会因为占位功能尚未实现而退回所有本地项目共用同一份旧工作区数据的模式。

## 15. 本次目标未决定的事项

下列问题值得后续确认，但不应阻挡已经明确的协作模型，也不应在文档中伪装成已确认要求：

| 待确认事项 | 已知约束 | 仍需决定的内容 |
| --- | --- | --- |
| 登录后的默认入口 | 无独立工作区选择；项目列表负责选择或新建 | 默认显示列表、恢复上次项目，还是有条件自动进入 |
| 左侧全局导航 | 不能破坏项目页功能的归属和权限 | 新对话、定时任务、收件箱、技能中心等是项目级、个人级还是授权汇总 |
| 动态产品形态 | 属于当前项目，允许逐步实现 | 会话、活动流、变更记录或其组合 |
| 计划与任务关系 | 都不能跨项目串数据 | 计划是否驱动执行任务，还是独立协作规划 |
| 角色权限表 | 角色属于项目，不能在项目间继承 | 角色名称及邀请、编辑、删除、执行的具体权限 |
| 智能体所有权与复用 | 与人类成员管理分开；使用范围受项目授权 | 账号资产、项目资产或多项目授权资产 |
| 浏览器协作策略 | 浏览器资源属于项目，实际会话也要隔离 | 并发控制、控制锁、持久登录及敏感凭据策略 |
| 项目生命周期 | 不能影响无关项目成员与数据 | 创建限制、归档、删除、恢复及所有权转移 |
| 项目公开能力 | 页面链接不应默认赋予成员权限 | 是否支持公开项目、公开快照或外部只读共享 |
| 存量迁移方案 | 不能凭本地分类推断资源归属 | 本地卡片与计划如何导入，旧容器如何映射 |
| 内部名称迁移 | 用户不再管理独立工作区 | 是否及何时修改表名、API、SDK 命令和事件名称 |

当前用户没有要求新增组织、部门或另一层团队空间，也没有要求每个用户先创建一个隐藏个人工作区。不能为了方便复用旧结构，就将这些内容默认加入产品模型。

## 16. 如何判断最终是否真正达成目标

最终需要同时满足三个层面：

1. **产品层**：用户只需要理解账号和项目，不需要理解另一个独立协作空间；项目列表与项目页面构成完整进入流程。
2. **协作层**：同一项目成员共享服务器维护的内容，成员关系和角色管理在项目内成立；不同项目彼此独立。
3. **执行层**：请求、缓存、订阅、关联资源、智能体工具和后台任务都保持明确的项目范围，界面切换不会造成数据或权限混用。

以下结果都不能单独算作完成：把菜单名称改为项目、去掉工作区选择按钮、给页面加 `projectId`、建立新的项目表、对会话名称加前缀，或仅在列表中做前端过滤。

**只有当项目本身成为成员、内容、权限与执行上下文共同围绕的协作实体，原工作区职责才算真正交接完成。**
